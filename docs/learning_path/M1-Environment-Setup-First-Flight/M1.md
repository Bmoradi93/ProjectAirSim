# Module 1 — Environment Setup & First Flight (Live Unreal Simulation)

## 1. Running Your First Flight (`pixi run hello-drone`)

In this module we fly a quadrotor inside the live **Unreal Engine 5 `Blocks`** simulation (rather than the headless runtime) using the Pixi workspace environment defined in `pixi.toml`.

### Step-by-Step Workflow

1. **Start the Simulator Host (Terminal 1 — inside the Docker container)**:
   Launch the Unreal Editor with the `Blocks` project:
   ```bash
   $UE_ROOT/Engine/Binaries/Linux/UnrealEditor-Linux-DebugGame \
     /workspace/ProjectAirSim/unreal/Blocks/Blocks.uproject
   ```
   Once the editor opens, press the green **Play** button in the toolbar.
   - At this point, the `ProjectAirSim` plugin initializes `SimLibs` and starts listening on TCP ports **8989** (Pub/Sub topics) and **8990** (Req/Rep services).
   - Notice that the world starts **empty** (no drone yet)—the scene is constructed dynamically when a client connects and loads a configuration.

2. **Run the Client Script (Terminal 2)**:
   From the repository root, run the `hello-drone` Pixi task:
   ```bash
   pixi run hello-drone
   ```
   *(Defined in `pixi.toml` as `python hello_drone.py` with working directory `client/python/example_user_scripts`.)*

3. **What Happens During Execution**:
   - The client connects to `127.0.0.1:8989` and `127.0.0.1:8990`.
   - `World` sends `sim_config/scene_basic_drone.jsonc` (and its nested `robot_quadrotor_fastphysics.jsonc`) to the simulator, spawning `Drone1` at NED `(-1.0, 8.0, -4.0)` with a `-45°` yaw.
   - Three OpenCV windows pop up via `ImageDisplay`: `ChaseCam`, `RGB-Image` (downward RGB), and `Depth-Image` (downward depth).
   - `Drone1` arms, takes off to 3 m above its spawn point, climbs 4 m (`v_down = -1.0` for 4 s), descends 4 m (`v_down = +1.0` for 4 s), lands, disarms, and disconnects cleanly.

## 2. The Four Core Python Client Classes

Every Python script in Project AirSim is built around four primary classes in `client/python/projectairsim/src/projectairsim/`:

| Class | Source File | Responsibility | Network Channel |
| :--- | :--- | :--- | :--- |
| **`ProjectAirSimClient`** | `client.py` | Owns the NNG sockets (`pynng.Pair0` on port **8989** for topics, `pynng.Req0` on port **8990** for services), background topic-receive thread, and MessagePack serialization. | TCP `8989` & `8990` |
| **`World`** | `world.py` | Loads and resolves the JSONC scene, robot, and environment-actor configs into a single dictionary, calls `/Sim/LoadScene`, and exposes world-level RPCs (clock control, weather, time-of-day, object spawning). | Port `8990` (Services) |
| **`Drone`** *(inherits `Robot`)* | `drone.py` / `robot.py` | Binds to a specific named robot actor (e.g., `"Drone1"`) in the loaded `World`. Builds the `drone.sensors` and `drone.robot_info` topic path maps from the loaded config and exposes flight control RPCs. | Port `8989` (Topics) & Port `8990` (Services) |
| **`ImageDisplay`** | `image_utils.py` | Optional client-side OpenCV GUI helper thread that receives decoded camera dictionaries from topic callbacks and renders them in sub-windows. | Local client memory |

## 3. Anatomy of `hello_drone.py` — The 6-Phase Client Lifecycle

Every Project AirSim client script follows the same six-phase structure. Below is how `client/python/example_user_scripts/hello_drone.py` maps to what happens under the hood.

```
[Phase 1: Connect]       client = ProjectAirSimClient() ──► client.connect()
                                │
[Phase 2: Load & Bind]   world = World(client, "scene_basic_drone.jsonc")
                         drone = Drone(client, world, "Drone1")
                                │
[Phase 3: Subscribe]     client.subscribe(drone.sensors[...], callback)
                                │
[Phase 4: Arm & Enable]  drone.enable_api_control() ──► drone.arm()
                                │
[Phase 5: Async Flight]  task = await drone.move_by_velocity_async(...)
                         await task
                                │
[Phase 6: Teardown]      drone.disarm() ──► drone.disable_api_control()
                         client.disconnect()  (inside `finally:` block)
```

### Phase 1 — Connect to the Simulator (`lines 18–25`)
```python
client = ProjectAirSimClient()
client.connect()
```
- Defaults to `address="127.0.0.1"`, `port_topics=8989`, `port_services=8990`.
- `client.connect()` dials two NNG TCP sockets:
  - `self.socket_topics = pynng.Pair0(...)` → `tcp://127.0.0.1:8989`
  - `self.socket_services = pynng.Req0(...)` → `tcp://127.0.0.1:8990`
- *Note*: The topic socket is a single-consumer `Pair0` channel. If an external bridge (such as the ROS 2 C++ node) already owns port `8989`, a second script can call `client.connect_services()` instead of `client.connect()` to send control commands on port `8990` without competing for the topic stream.

### Phase 2 — Load the Scene & Bind the Drone Actor (`lines 28–31`)
```python
world = World(client, "scene_basic_drone.jsonc", delay_after_load_sec=2)
drone = Drone(client, world, "Drone1")
```
- **`World(...)`**:
  1. Reads `sim_config/scene_basic_drone.jsonc` using `commentjson` (since Project AirSim configs use JSON-with-comments).
  2. Inline-expands every `"robot-config"` (here `robot_quadrotor_fastphysics.jsonc`) and `"env-actor-config"` referenced in the scene.
  3. Sends the `/Sim/LoadScene` RPC over port `8990`, sets `world.parent_topic = "/Sim/SceneBasicDrone"`, queries `/$topics` to refresh the server's active topic list, and sleeps for `delay_after_load_sec=2` so Unreal finishes spawning actors and initializing render targets.
- **`Drone(client, world, "Drone1")`**:
  1. Looks up `"Drone1"` inside `world.get_configuration()["actors"]`.
  2. Sets `drone.parent_topic = "/Sim/SceneBasicDrone/robots/Drone1"`.
  3. Inspects the robot's `"sensors"` array in the loaded JSONC config and populates `drone.sensors` and `drone.robot_info` with the exact NNG topic path strings—and prints them to the console via `self.log_topics()`.

### Phase 3 — Subscribe to Sensor Topics (`lines 36–58`)
```python
client.subscribe(
    drone.sensors["DownCamera"]["scene_camera"],
    lambda _, rgb: image_display.receive(rgb, rgb_name),
)
```
- `drone.sensors` is a nested dictionary of **topic path strings** constructed from the robot config:
  - `drone.sensors["Chase"]["scene_camera"]` → `"/Sim/SceneBasicDrone/robots/Drone1/sensors/Chase/scene_camera"`
  - `drone.sensors["DownCamera"]["scene_camera"]` → `"/Sim/SceneBasicDrone/robots/Drone1/sensors/DownCamera/scene_camera"`
  - `drone.sensors["DownCamera"]["depth_camera"]` → `"/Sim/SceneBasicDrone/robots/Drone1/sensors/DownCamera/depth_camera"`
  - `drone.robot_info["actual_pose"]` → `"/Sim/SceneBasicDrone/robots/Drone1/actual_pose"`
- On the first `client.subscribe(topic_path, callback)` call, `ProjectAirSimClient` lazily spawns a background Python thread (`self.recv_topic_thread`) that reads frames from port `8989`, unpacks the MessagePack payload, and invokes `callback(topic_obj, message_dict)`.

### Phase 4 — Enable API Control & Arm (`lines 63–64`)
```python
drone.enable_api_control()
drone.arm()
```
- Both are **synchronous** Req/Rep calls (`client.request(...)`) over port `8990`:
  - `enable_api_control()` (`/Sim/SceneBasicDrone/robots/Drone1/EnableApiControl`): switches the flight controller from manual/RC input mode to programmatic API control. If skipped, motion RPCs are rejected.
  - `arm()` (`/Sim/SceneBasicDrone/robots/Drone1/Arm`): arms the virtual motors so the controller can spin the rotors.

### Phase 5 — The Two-Stage `async`/`await` Pattern & NED Coordinates (`lines 68–106`)

Look closely at how every motion command in `hello_drone.py` is awaited **twice**:

```python
# Stage 1: Send the RPC request and receive an asyncio.Task handle
move_up_task = await drone.move_by_velocity_async(
    v_north=0.0, v_east=0.0, v_down=-1.0, duration=4.0
)

# Stage 2: Wait for the maneuver itself to complete in the simulator
await move_up_task
```

#### Why are there two `await`s?
Inside `ProjectAirSimClient.request_async()` (`client.py:284–309`):
```python
ctx = self.socket_services.new_context()
await ctx.asend(request_packed)                      # <-- 1st await: sends RPC over TCP 8990

response = ctx.arecv_msg()
post_proc_task = asyncio.create_task(                # <-- wraps the pending server reply
    self.postprocess_response_async_with_callback(response, callback)
)
return post_proc_task                                # <-- returned to caller
```
1. **First `await` (`task = await drone.move_..._async(...)`)**: Opens an independent NNG request context (`new_context()`) on port `8990`, transmits the command packet to the simulator, and immediately returns an `asyncio.Task` that is waiting on the server's reply.
2. **Second `await` (`await task`)**: Waits until the simulator's flight controller finishes executing the 4-second maneuver and sends back the completion reply packet.

#### Why is this useful?
Because the first `await` returns immediately after dispatching the command, you can:
- **Poll or do work while the drone is moving** (shown in `hello_drone.py` lines 97–98):
  ```python
  while not move_down_task.done():
      await asyncio.sleep(0.005)
  ```
- **Preempt an in-flight command** by issuing a new `move_*_async` call before the previous task completes.
- **Fly multiple drones concurrently** in the same script by dispatching tasks to `drone1` and `drone2` and waiting on both with `await asyncio.gather(task1, task2)`.

#### Coordinate System Trap: NED (North-East-Down)
Project AirSim uses the aerospace **NED** convention for world and velocity commands:
- `+X` / `v_north > 0` → **North** (Forward)
- `+Y` / `v_east > 0`  → **East** (Right)
- `+Z` / `v_down > 0`  → **Down** (Toward the ground)

Therefore:
- **Climbing / altitude above origin is negative `Z`**: In `scene_basic_drone.jsonc`, `"xyz": "-1.0 8.0 -4.0"` spawns the drone `4 m` **above** the origin, and `v_down = -1.0` commands the drone to climb **upward** at `1 m/s`.
- **Descending is positive `Z`**: `v_down = +1.0` commands the drone to descend **downward** at `1 m/s`.

### Phase 6 — Teardown & Disconnect (`lines 110–125`)
```python
        drone.disarm()
        drone.disable_api_control()
    except Exception as err:
        projectairsim_log().error(f"Exception occurred: {err}", exc_info=True)
    finally:
        client.disconnect()
        image_display.stop()
```
- Always place `client.disconnect()` inside a `finally:` block.
- `client.disconnect()` unsubscribes from all active topics, stops `recv_topic_thread`, and closes both NNG sockets (`8989` and `8990`) so the simulator's `Pair0` topic socket is freed for your next script run.

## 4. Quick Reference: Synchronous vs. Asynchronous Drone APIs

| Category | Method | Sync / Async | Underlying RPC Method |
| :--- | :--- | :--- | :--- |
| **Lifecycle / Safety** | `drone.enable_api_control()` | Sync | `<robot>/EnableApiControl` |
| | `drone.disable_api_control()` | Sync | `<robot>/DisableApiControl` |
| | `drone.arm()` / `drone.disarm()` | Sync | `<robot>/Arm`, `<robot>/Disarm` |
| **State Queries** | `drone.get_ground_truth_kinematics()` | Sync | `<robot>/GetGroundTruthKinematics` |
| | `drone.get_ground_truth_pose()` | Sync | `<robot>/GetGroundTruthPose` |
| | `drone.get_landed_state()` | Sync | `<robot>/GetLandedState` |
| **Flight Maneuvers** | `await drone.takeoff_async()` | Async (2-stage) | `<robot>/Takeoff` |
| | `await drone.land_async()` | Async (2-stage) | `<robot>/Land` |
| | `await drone.hover_async()` | Async (2-stage) | `<robot>/Hover` |
| | `await drone.go_home_async()` | Async (2-stage) | `<robot>/GoHome` |
| | `await drone.move_by_velocity_async(v_north, v_east, v_down, duration)` | Async (2-stage) | `<robot>/MoveByVelocity` |
| | `await drone.move_to_position_async(north, east, down, velocity)` | Async (2-stage) | `<robot>/MoveToPosition` |
| | `await drone.move_on_path_async(path, velocity)` | Async (2-stage) | `<robot>/MoveOnPath` |
| | `await drone.rotate_to_yaw_async(yaw)` | Async (2-stage) | `<robot>/RotateToYaw` |
