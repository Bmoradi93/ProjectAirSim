# Module 0 — Orientation & Mental Model

## 1. The Three-Layer Architecture

Project AirSim is decoupled into three distinct layers:

```
┌────────────────────────────────────────────────────────────────────────┐
│                          3. CLIENT LAYER                               │
│  Python Client (projectairsim)  │  C++ Standalone Client  │  ROS 2 Node │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │ NNG over TCP
                                     │ Port 8989 (Pub/Sub Topics)
                                     │ Port 8990 (Req/Rep Services)
                                     ▼
┌────────────────────────────────────────────────────────────────────────┐
│                           2. HOST LAYER                                │
│                                                                        │
│   Choice A: Headless Runtime               Choice B: Unreal Engine 5   │
│   (projectairsim-runtime)                  (Blocks.uproject + Plugin)  │
│   • Flat-ground collision                  • 3D Meshes & Nanite/Lumen  │
│   • No GPU / display required              • Rendered Sensors (Camera, │
│   • Fast physics & control CI                GPU LiDAR, Segmentation)  │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │ Embeds / links
                                     ▼
┌────────────────────────────────────────────────────────────────────────┐
│                        1. SIM LIBS (C++ CORE)                          │
│  core_sim/       - Simulation loop, scene & actor management, clock    │
│  physics/        - FastPhysics, JSBSim, Simulink integrations          │
│  vehicle_apis/   - Flight controllers (SimpleFlight, PX4, ArduPilot)   │
│  simserver/      - NNG RPC server, MessagePack serialization           │
│  mavlinkcom/     - MAVLink transport protocol                          │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. Key Paradigm Shifts: AirSim v1 vs. Project AirSim

| Concept | Classic AirSim (v1) | Project AirSim |
| :--- | :--- | :--- |
| **Engine Coupling** | Hard-coupled to Unreal Engine game loop | Decoupled C++ core (`SimLibs`). Can run standalone without Unreal (`projectairsim-runtime`). |
| **World & Scene Init** | Static `settings.json` loaded at simulator launch | Simulator starts empty. **Client sends JSONC scene config dynamically** (`world = World(client, "scene.jsonc")`). |
| **Network Transport** | msgpack-rpc over custom TCP socket | **NNG (Nanomsg Next Gen)** over TCP: Topics on **8989**, Services on **8990**. |
| **Vehicle Extensibility**| Fixed vehicle types in C++ hierarchy | Configurable links, joints, actuators, and sensor arrays via JSONC schema. |
| **Sensors** | CPU-side raycasts and synchronous render targets | Compute-shader GPU LiDAR, asynchronous image encoding, shared-memory FastDDS profile for ROS 2. |

## 3. Communication Model

Project AirSim exposes two dedicated communication channels via NNG:

1. **Port 8989 (Topics — Publish / Subscribe)**:
   - High-throughput unidirectional streaming from simulator to clients.
   - Sensor streams: Camera frames, LiDAR point clouds, IMU, GPS, Magnetometer, Barometer.
   - Telemetry: Kinematic state, `/actual_pose`, `/velocity`.

2. **Port 8990 (Services — Request / Response)**:
   - Synchronous RPC calls for commands and queries.
   - Lifecycle: `load_scene`, `reset`, `pause`, `step`.
   - Control: `arm`, `disarm`, `takeoff`, `land`, `move_by_velocity_async`, `move_to_position_async`.

## 4. Checkpoint Flow: `move_by_velocity_async()` to `/actual_pose`

Tracing a complete control command and telemetry loop:

```
[User Python Script]
   │
   │ 1. await drone.move_by_velocity_async(vx=2.0, vy=0.0, vz=0.0, duration=3.0)
   ▼
[projectairsim.Client (Python)]
   │
   │ 2. Serializes RPC request with MessagePack
   │    Sends over TCP to 127.0.0.1:8990 (Services Socket)
   ▼
═════════════════════ Process Boundary (TCP / Port 8990) ═════════════════════
   ▼
[SimServer (C++ in Host Process)]
   │
   │ 3. Deserializes MessagePack request
   │    Dispatches to MultirotorApi / VehicleApi instance for "Drone1"
   ▼
[Vehicle API (SimpleFlight / PX4)]
   │
   │ 4. Converts target velocity vector into motor mixer outputs / rotor thrust commands
   ▼
[Physics Engine (FastPhysics / JSBSim)]
   │
   │ 5. Calculates forces & torques; integrates equations of motion for time step `dt`
   │    Computes new pose: P_{t+dt} = P_t + V * dt
   ▼
[Host Synchronization (Unreal Actor or Runtime Collision)]
   │
   │ 6. Updates transform of the vehicle link; evaluates ground/mesh collisions
   ▼
[SimServer Topic Publisher]
   │
   │ 7. Packs new Kinematics/Pose into MessagePack payload
   │    Publishes to Topic: `/ProjectAirsim/<scene>/robots/Drone1/actual_pose`
   ▼
═════════════════════ Process Boundary (TCP / Port 8989) ═════════════════════
   ▼
[projectairsim Subscriber (Python Client)]
   │
   │ 8. Receives bytes on Port 8989; triggers registered callback
   ▼
[User Callback / State Listener]
   Receives updated Pose (position: x, y, z; orientation: quaternion)
```

## 5. Deconstructing "Blocks" vs. ProjectAirSim Plugin vs. SimLibs

A common point of confusion is how Unreal Engine, `Blocks`, and ProjectAirSim relate:

```
┌────────────────────────────────────────────────────────┐
│  CLIENTS (Python / ROS 2 / C++)                        │
│  "Fly forward at 2 m/s", "Give me camera feed"         │
└───────────────────────────┬────────────────────────────┘
                            │ NNG / MessagePack (TCP 8989 / 8990)
                            ▼
┌────────────────────────────────────────────────────────┐
│  SimLibs (C++ Core: physics/, vehicle_apis/, etc.)    │
│  • Computes aerodynamics, thrust, motor mixing         │
│  • Integrates equations of motion                      │
│  • Calculates where the vehicle is in space            │
└───────────────────────────┬────────────────────────────┘
                            │ C++ API / Transform Sync
                            ▼
┌────────────────────────────────────────────────────────┐
│  ProjectAirSim UE Plugin (The Bridge)                  │
│  • Embeds SimLibs inside Unreal's game loop            │
│  • Translates SimLibs coordinates to Unreal Actors     │
│  • Hooks Unreal Cameras & GPU LiDAR to SimServer       │
└───────────────────────────┬────────────────────────────┘
                            │ Native Unreal Game Engine
                            ▼
┌────────────────────────────────────────────────────────┐
│  Blocks (unreal/Blocks/Blocks.uproject)                │
│  • The 3D Environment (Meshes, Textures, Sky, Sun)     │
│  • Unreal's Nanite geometry, Lumen lighting, Materials │
└────────────────────────────────────────────────────────┘
```

### What each part specifically does:

1. **`Blocks` (`unreal/Blocks/Blocks.uproject`)**:
   - A standard Unreal Engine 5 project containing a sandbox environment (`BlocksMap.umap`).
   - Contains 3D meshes (cubes, ramps, ground), lighting (Lumen), and sky atmosphere.
   - It is intentionally minimal so developers don't need a 100 GB map to test code.
   - Any custom Unreal environment (city, forest, offshore wind farm) can replace `Blocks` simply by enabling the `ProjectAirSim` plugin in its `.uproject`.

2. **`ProjectAirSim` Plugin (`unreal/Blocks/Plugins/ProjectAirSim/`)**:
   - The native bridge between Unreal Engine and the C++ simulation core (`SimLibs`).
   - When Unreal ticks a frame, the plugin steps `SimLibs`.
   - Reads the newly computed vehicle pose from `SimLibs` and positions the Unreal visual actor (`AUnrealRobot`).
   - Grabs render targets (RGB cameras, depth buffers, GPU compute shaders for LiDAR) and passes those buffers into `SimServer` for serialization.

3. **Why this matters**:
   - Unreal Engine does **not** own the flight dynamics or controller logic; `SimLibs` does.
   - If you need **cameras, GPU LiDAR, or complex 3D world meshes**, you launch **`Blocks`** (with the plugin).
   - If you only need **flight control, kinematics, state estimation, or GPS/IMU data**, you launch the **headless runtime (`projectairsim-runtime`)**.
   - Your Python, C++, or ROS 2 client code remains 100% identical between the two—it talks to the exact same ports (8989 / 8990) using the exact same protocol.
